# Frozen practical presentation and handoff protocol — Wine Quality, forward v3.5

This directory is an evaluator plan for a new-source, practical presentation trial. It is distinct from the main 3.4.0 official benchmark, its VisEval scores and its negative polish evidence. Preserve those records unchanged. This trial cannot be called a new official VisEval score, a retrospective repair of that benchmark, a pure-method causal A/B test or demonstrated real-world comprehension improvement.

## Scope, blindness and precommitment

- The plan author does not inspect source CSVs, expected source answers, method bodies or peer outputs. This plan contains no source-valued results. The bounded protocol-writing task has a 15-minute limit and no child agents.
- Latest candidate 3.5 was frozen at `2026-10-15T03:43:44Z`, before the owner's new source answers, as reported by the coordinating owner. The owner retains the actual frozen package/hash evidence. This plan does not independently certify that freeze.
- Candidate activation is a composite: the owner reports 76 methods including the original six core methods and actual frontend/art-direction complements. Interpret condition comparisons accordingly; no isolated causal attribution to one method.
- Before any author starts, seal this plan, the public brief, assertion specification, synthetic fixtures/expected mechanics, condition packages, equal author prompts and timing rule. Record hashes and the common model/version/settings in the owner's manifest.
- The source owner independently obtains the UCI red/white source snapshot, preserves original bytes, records origin/hash/parser and computes the private oracle using `PRIVATE_ASSERTIONS.md`. Do this after method freeze and before inspecting author results. Do not derive truth from report agreement.
- Only `PUBLIC_BRIEF.vi.md`, the same source package/manifest and the privately assigned condition go to each author. Private evaluator files and oracle stay outside author-accessible context. Readers never receive methods, condition identities, oracle or peer-reader answers.
- No benchmark score or winner is prefilled. Do not invent counts to complete an unavailable oracle. If parsing/oracle is unresolved, continue layout inspection if useful but mark source-accuracy conclusions pending.

## Delivery verification without owner repair

Give each sealed package a neutral alias in a private randomized mapping. Verify artifact existence and offline opening using the delivered entry point, not an owner-made preview. In a fresh temporary location, run its documented rebuild recipe unchanged, with network disabled and the declared runtime. Capture the command, environment, exit status and any manual steps actually needed. Do not install unrecorded online dependencies or fix a path/script for the author.

Compare regenerated facts against the sealed independent oracle, then compare displayed numbers, chart geometry/labels, source files and disclosures against those facts. Check exact source bytes; preserve original records and one-based parsed-data-row identity. A renderer opening successfully does not establish data correctness. A source calculation passing does not establish polish or reader usability.

Any rebuild comparison may ignore declared nondeterministic metadata such as generation timestamp only if all facts and substantive rendered content remain identical; record the difference rather than editing it away. Test unsupported dependence on network by opening the package offline. Record unavailable runtime honestly; do not infer a build pass from its documentation.

## Matched capture

Use one capture owner and the same browser/version/font environment for all conditions. Capture at CSS widths **960 and 390**, both at **DPR 2**, respectively **960×900** and **390×844**, 100% browser zoom. Ordered viewport tiles overlap by 160 CSS pixels (stride viewport height minus 160), plus unaltered full-page images. Record sticky/overlay problems rather than changing the report. Do not rescale text or crop away inconvenient content for one condition.

For each width, retain: initial viewport, the entire original page in ordered sections/full-page capture, and every original disclosure, caveat, source note, appendix and handoff instruction. Capture the original initial state first. Then expand each native disclosure or follow each local report/appendix link needed to expose original content, recording the interaction. Keep all resulting views in reading order. If a disclosure cannot be opened, record the failure. Do not insert, remove, rewrite or reflow content for evaluation. Capture horizontal overflow, unreadably small labels, overlays and broken local links as observed.

Review desktop and mobile for heading/claim hierarchy, readable type, chart/table interpretation, denominator access, narrative coherence, spacing, clipping/overlap, useful navigation, and full disclosure access. Check any author-created loading, empty, error or interaction state that exists and can be reached with the delivered interface. Do not add unsupported states or demand an application when a static page suffices.

## Fresh reader tasks

Use two fresh reader contexts per condition, **ten independent contexts total**, all on the same common reader model/version/settings. These are model readers, not human participants. Provide the neutral package's common matched captures/rendered report and the fixed manager questions from `PRIVATE_ASSERTIONS.md`; provide no oracle, method, condition label, source analysis or other reader answer. Record raw answers and evidence locations before scoring.

First assess the report alone for managerial reading. Then provide that package's handoff files and the identical private synthetic recipient task/fixtures. Ask for the actual completed template/action row, not a self-rating. Do not let later file access revise the first manager answers. Use a uniform **combined 20-minute wall-clock budget per reader**, beginning when the initial reader task is dispatched. Reader submits manager answers and pauses; owner seals those bytes before supplying any handoff files or SYN fixtures. Record dispatch deadline, stage transition and final/deadline state. Stage two uses only the remaining combined budget; no time extension. Use the same stage instructions and access policy for all ten. Record unreadable/unavailable material and abstentions. Do not correct or coach readers.

The fixture task tests manual handling of four synthetic records: raw missing/unknown/not-done values remain unchanged, incomplete cases stay HOLD, the all-done case is READY FOR REVIEW only, and a new follow-up is assigned without fabricating the missing reviewer. It tests usable delivery and permission boundaries, not tasting or actual staff work.

## Eight fresh visual pair judgments

Compare latest candidate with each of the other four conditions twice: **eight fresh pairwise contexts**, separate from all ten task readers. Use the same model/version/settings. Pair repetition swaps left/right positions; use neutral aliases and a presealed order. Each judgment sees the same complete 960/390 capture sets for both sides, including all original disclosures. Do not give a prettier excerpt to one side or mix capture scales.

Use this exact judgment request for every pair:

> Bạn có hai bộ ảnh đầy đủ của trang bên trái và bên phải, gồm máy tính, điện thoại và phần giải thích gốc. Đánh giá riêng hai mặt: (1) độ hoàn thiện thẩm mỹ; (2) dễ đọc và dùng cho quản lý cần hiểu kết quả rồi giao việc. Với mỗi mặt, nêu bằng chứng cụ thể trước rồi chọn `left`, `right`, `tie` hoặc `cannot judge`. Xem thứ bậc thông tin, chữ/biểu đồ/bảng, điện thoại, việc tìm giới hạn/nguồn và bước tiếp theo. Tách sở thích thẩm mỹ khỏi tính đúng của số liệu mà ảnh không đủ để xác minh. Không suy đoán phương pháp hoặc danh tính tác giả.


For each dimension separately, map left/right to condition before resolving swapped episodes. Both mapped votes must agree to award a preference; any disagreement becomes tie. Any cannot-judge makes that dimension unresolved. Retain the raw explanations and votes; never combine these dimensions into an invented overall score. One swapped pair is not two independent human opinions; report the model/context count and order sensitivity.

## Outcome ledger and decision rule

Keep these independent, with raw denominators and failures visible:

1. **Source integrity and interpretation:** M01–M14 artifact checks, reconciliations, unsupported claims, duplicate handling and hypothetical-rule framing. Report exact failed checks; a visual win cannot cancel a wrong primary number or an invented approval.
2. **Manager task performance:** correctness and evidence access for the fixed questions, per reader and condition. Distinguish wrong, absent and not-ascertainable answers. Do not convert reader confidence into correctness.
3. **Recipient handoff:** four statuses, raw-field preservation and the one usable new action, using the expected mechanics. A status-only explanation without a usable new record does not complete the task.
4. **Rendering and practical polish:** direct desktop/mobile observations and the eight raw pairwise judgments. Report each candidate-versus-baseline pair separately, including swapped-order disagreement and ties.
5. **Portable delivery:** offline read, retained source, unchanged rebuild, facts/render agreement and material manual friction.

Do not combine these into an invented official score. A condition is ready for this bounded hypothetical handoff only if the required files are usable, primary facts and interpretation are correct, mandatory HOLD/READY FOR REVIEW semantics are preserved, the practical recipient task is complete, and required mobile content is readable/accessible. Otherwise label the exact remaining limitation. Even a ready result does not authorize a real audit.

For the latest candidate, distinguish **passed required checks**, **preferred in these fresh model comparisons**, **mixed result**, **incomplete**, and **unresolved**. Claim presentation improvement only to the extent supported by matched observations, raw preferences and comparable reader tasks; disclose failures and the composite condition. No statistical significance, human performance, general quality advantage, real wine-quality validation or production readiness follows from this small trial.

## Sealed common execution settings

Exact backend model identifier, token usage and hidden sampling settings are unavailable; record them as unknown rather than invent them. Installed skill catalog remains the same 3.3 catalog plus retained complementary resources throughout all runs. Only frozen assigned bundles are authorized method context. Earliest three authors run together; next two start as slots free. Wave effects are a limitation. Source oracle final bytes are sealed before any authors.
